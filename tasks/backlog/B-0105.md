# B-0105 — Booking CANCEL API (환불 스텁 + 재고 복구)



## Goal
사용자가 예약을 취소할 수 있어야 하며, 상태에 따라 재고 복구가 정확해야 한다.
    - HOLD 취소: hold를 감소
    - BOOKED 취소: sold를 감소(환불) + 필요 시 penalty/voucher 정책은 v2



## Scope
- `POST /v1/bookings/{bookingId}/cancel`
    - 상태 전이:
      - HOLD → CANCELLED (inventory.hold 감소)
      - BOOKED → CANCELLED (inventory.sold 감소, refund stub)
    - outbox:
      - `BookingCancelled`



## Non-goals
- 부분 취소(일부 nights) v2
    - 취소 수수료/환불 정책 엔진 v2



## API Contract
### POST /v1/bookings/{bookingId}/cancel
- `X-Request-Id` (optional): 클라이언트가 생성한 요청 ID (없으면 서버 생성)
- `Idempotency-Key` (쓰기 API 필수): UUID 권장. 동일 요청 재시도 시 동일 결과 반환
- `Authorization` (optional in MVP): `Bearer <token>` (MVP에서는 `X-User-Id`로 대체 가능)
- `X-User-Id` (MVP only): 숫자 사용자 ID (인증 도입 전까지 임시)
Request:
```json
{
  "reason": "CHANGE_OF_PLANS"
}
```
200 Response:
```json
{
  "request_id": "01J0...",
  "data": {
    "booking_id": "bkg_01J0...",
    "status": "CANCELLED",
    "cancelled_at": "2026-02-07T14:11:00Z"
  }
}
```

Error:
- 404 `NOT_FOUND`
- 409 `BOOKING_STATE_CONFLICT` (이미 CANCELLED 등)
- 409 `INVENTORY_INVARIANT_VIOLATION` (hold/sold 부족)



## SQL (inventory restore)
```sql
-- 상태에 따라 다른 복구:
    -- HOLD 취소
    UPDATE inventory_night
    SET hold = hold - :rooms
    WHERE room_type_id=:roomTypeId AND stay_date=:stayDate AND hold >= :rooms;

    -- BOOKED 취소
    UPDATE inventory_night
    SET sold = sold - :rooms
    WHERE room_type_id=:roomTypeId AND stay_date=:stayDate AND sold >= :rooms;
```



## Transaction
1) booking row 조회 + 락(선택: FOR UPDATE)
    2) booking_night 조회(오름차순)
    3) 상태별 inventory 감소(조건부) → 실패 시 롤백
    4) refund stub(BOOKED인 경우만)
    5) booking.status=CANCELLED, cancelled_at set
    6) outbox_event insert(BookingCancelled)
    7) COMMIT



## Testing
- HOLD 취소: hold 감소 확인
    - BOOKED 취소: sold 감소 확인
    - 동시 cancel/confirm 경쟁:
      - confirm과 cancel이 동시에 오면 1개만 승리(booking 락으로 직렬화)



## Acceptance Criteria
- 취소 후 재고가 정확히 복구된다
    - 중복 취소는 idem으로 안전하게 처리된다
