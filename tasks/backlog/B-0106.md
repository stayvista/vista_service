# B-0106 — HOLD 만료 회수(Job/Scheduler)



## Context
HOLD는 TTL이 있는 임시 점유다. 만료된 HOLD를 회수하지 않으면:
    - 재고가 영구히 잠겨 판매 불가
    - CS/운영 이슈 증가

    따라서 주기적으로 만료 HOLD를 찾아 **재고를 복구**하고 booking을 EXPIRED/CANCELLED로 전환해야 한다.



## Goal
- 만료된 HOLD를 안전하게 회수한다(중복 실행/병렬 실행에도 안전).
    - 회수 과정에서 과도한 락/데드락을 유발하지 않는다.



## Scope
- 스케줄러(예: 1분 주기) 또는 별도 worker
    - 대상:
      - `booking.status='HOLD' AND expires_at < now`
    - 처리:
      - booking_night 기반으로 inventory.hold 감소(조건부)
      - booking.status='EXPIRED'
      - outbox_event: `BookingExpired`(선택)
    - 병렬 실행:
      - `FOR UPDATE SKIP LOCKED`로 배치 처리



## SQL pattern
```sql
-- batch로 만료 booking을 가져오고 락을 건다
    SELECT id, room_type_id, rooms
    FROM booking
    WHERE status='HOLD'
      AND expires_at < NOW(3)
    ORDER BY id
    LIMIT 200
    FOR UPDATE SKIP LOCKED;
```



## Processing steps
- 각 booking에 대해:
      1) booking_night 조회(오름차순)
      2) inventory_night에서 hold 감소(hold>=rooms 조건)
      3) booking.status='EXPIRED', expired_at set
      4) (선택) outbox insert
    - 예외 처리:
      - hold가 부족하면 데이터 이상 → `INVENTORY_INVARIANT_VIOLATION` 로그/알람



## Observability
- Metrics:
      - `booking_expiry_scanned_total`
      - `booking_expired_total`
      - `booking_expiry_fail_total`
    - Alert:
      - fail_total > 0
      - expired_total 급증(봇/결제장애 신호)



## Testing
- Integration:
      - expires_at 과거인 booking을 넣고 job 실행 → inventory.hold 감소, status=EXPIRED
      - job을 2개 인스턴스로 동시에 실행 → 중복 처리 없음(SKIP LOCKED)



## Acceptance Criteria
- 만료 HOLD가 2분 내 회수된다(주기/배치 기준)
    - 중복 실행에도 재고가 과도하게 복구되지 않는다
