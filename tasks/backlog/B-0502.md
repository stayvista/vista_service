# B-0502 — Virtual Waiting Room(대기열) — 핫딜/오픈런 보호



## Context
특가/오픈런에서는 특정 숙소/룸타입(핫키)에 트래픽이 폭발한다.
    DB 락 대기/타임아웃이 늘어나면 전체 서비스가 느려진다.

    해결: **Virtual Waiting Room**
    - 예약 쓰기 경로 앞에 “입장 토큰”을 두고
    - 제한된 수만큼만 HOLD/CONFIRM을 시도하게 한다.



## Goal
- 핫키(특정 상품)에 대한 동시 시도를 제한하여 DB를 보호한다.
    - 사용자는 대기열에서 진행률/예상시간을 볼 수 있다.
    - 우회(토큰 위조/재사용)를 방지한다.



## Scope
- 대상 엔드포인트:
      - `POST /v1/bookings/holds`
      - `POST /v1/bookings/*/confirm`
      - `POST /v1/tickets/orders/holds`, `.../confirm`
    - 대기열 API:
      - `POST /v1/queue/join` (queue_key 기준)
      - `GET /v1/queue/status?ticket=...`
    - Gateway filter:
      - 큐가 ON이면 Queue-Token 없거나 invalid → 429 `QUEUE_REQUIRED`
      - valid token & turn reached → 통과
    - 저장소: Redis
      - queue: sorted set(가입 순서)
      - admitted set: 현재 입장 허용 사용자(동시성 제한)



## Queue key design
- `queue_key`는 핫키 단위로 만들기:
      - 예: `accom:{room_type_id}:{check_in}:{check_out}`
      - 예: `ticket:{event_id}`
    - coarse key(숙소 전체)로 하면 불필요한 대기 증가



## API Contract
### POST /v1/queue/join
Request:
```json
{
  "queue_key": "accom:2001:2026-02-10:2026-02-12"
}
```
201 Response:
```json
{
  "request_id": "01J0...",
  "data": {
    "queue_key": "accom:2001:2026-02-10:2026-02-12",
    "ticket": "qtk_01J0... (signed)",
    "position": 1532,
    "estimated_wait_seconds": 120
  }
}
```

### GET /v1/queue/status?ticket=...
200 Response:
```json
{
  "request_id": "01J0...",
  "data": {
    "state": "WAITING|ADMITTED|EXPIRED",
    "position": 120,
    "estimated_wait_seconds": 30,
    "admit_token": "qat_01J0... (signed, short TTL)"
  }
}
```



## Token model
- `ticket`(대기열 표): queue_key + user_id/ip + issued_at 를 서명(JWT/PASETO)
      - TTL: 30분
    - `admit_token`(입장권): 짧은 TTL(예: 30초)
      - Gateway는 이 admit_token만 검사하고 통과시킴



## Algorithm (Redis)
- join:
  - ZADD queue_zset score=now member=ticket_id
  - position = ZRANK
- admit loop(worker or on-demand):
  - admitted_count < MAX_ADMITTED 이면
    - ZPOPMIN(queue_zset)로 앞사람 꺼내 admitted_set에 넣고 TTL 부여
- status:
  - admitted_set에 있으면 ADMITTED
  - 아니면 queue_zset에서 rank를 보고 WAITING



## Protection / fairness
- 동일 사용자 중복 join 방지:
      - `SETNX queue:joined:{queue_key}:{user_id}` TTL 30m
    - refresh 정책:
      - admitted token은 짧게, 주기적으로 status 호출로 갱신
    - 봇 방지:
      - join에도 rate limit 적용(B-0501)



## Observability
- Metrics:
      - `queue_join_total`, `queue_admitted_total`
      - `queue_length{queue_key}` (샘플링)
      - `queue_wait_seconds` (histogram)
    - Alerts:
      - queue_length 급증
      - admitted_total=0인데 join_total만 증가(입장 루프 장애)



## Testing
- Integration(Redis):
      - 1000명 join 후 admit 100명 → 앞에서부터 admit 되는지
      - token 만료 시 EXPIRED로 처리되는지
      - gateway filter가 admit_token 없으면 429 반환하는지



## Acceptance Criteria
- 오픈런 시나리오(B-0601)에서 DB lock wait/timeout이 유의미하게 감소
    - 사용자는 대기열 상태를 볼 수 있다(U-0104에 연결)
