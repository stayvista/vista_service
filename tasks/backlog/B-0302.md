# B-0302 — Package Booking Saga(오케스트레이션)



## Context
패키지는 여러 리소스(숙소 재고 + 티켓 재고)를 **원자적으로** 확보/확정해야 한다.
    단일 DB 트랜잭션으로는 불가능하므로 Saga(보상 트랜잭션)로 해결한다.

    v1은 “오케스트레이터 방식”을 채택:
    - Package 서비스가 단계별로 HOLD/CONFIRM을 호출
    - 실패 시 이전 단계의 보상(CANCEL/RELEASE)을 호출



## Goal
- 패키지 구매에서 “부분 성공”이 남지 않도록 한다.
    - 오픈런에서도 과판매 0(각 컴포넌트는 DB로 보장)
    - 최종 일관성: confirm이 완료되면 모든 컴포넌트가 확정 상태다.



## Scope
- `POST /v1/packages/{packageId}/holds`
      - (1) Booking HOLD(숙소) 호출
      - (2) Ticket HOLD 호출
      - 둘 중 하나 실패 시 보상 호출로 원복
    - `POST /v1/packages/{packageId}/confirm`
      - (1) 숙소 confirm
      - (2) 티켓 confirm
      - 중간 실패 시 보상(cancel) 수행
    - 패키지 주문 상태:
      - HOLDING, HOLD, CONFIRMING, CONFIRMED, FAILED, CANCELLED
    - 멱등/재시도:
      - package hold/confirm도 Idempotency-Key 강제



## API Contract
### POST /v1/packages/{packageId}/holds
- `X-Request-Id` (optional): 클라이언트가 생성한 요청 ID (없으면 서버 생성)
- `Idempotency-Key` (쓰기 API 필수): UUID 권장. 동일 요청 재시도 시 동일 결과 반환
- `Authorization` (optional in MVP): `Bearer <token>` (MVP에서는 `X-User-Id`로 대체 가능)
- `X-User-Id` (MVP only): 숫자 사용자 ID (인증 도입 전까지 임시)
```json
{
  "check_in": "2026-02-10",
  "check_out": "2026-02-12",
  "rooms": 1,
  "ticket_quantity": 2
}
```
201 Response:
```json
{
  "request_id": "01J0...",
  "data": {
    "package_order_id": "pkg_01J0...",
    "status": "HOLD",
    "components": {
      "booking_id": "bkg_01J0...",
      "ticket_order_id": "tord_01J0..."
    },
    "expires_at": "2026-02-07T14:05:00Z"
  }
}
```

### POST /v1/packages/{packageId}/confirm
```json
{
  "package_order_id": "pkg_01J0...",
  "payment_token": "paytok_test"
}
```
200 Response:
```json
{
  "request_id": "01J0...",
  "data": {
    "package_order_id": "pkg_01J0...",
    "status": "CONFIRMED"
  }
}
```



## Saga Steps (HOLD)
1) PackageOrder 생성(status=HOLDING)
    2) Booking HOLD 호출
       - 실패 → PackageOrder=FAILED + 종료
    3) Ticket HOLD 호출
       - 실패 → Booking CANCEL(또는 hold release) 호출(보상) → PackageOrder=FAILED
    4) 둘 다 성공 → PackageOrder=HOLD + expires_at=min(component expires)



## Saga Steps (CONFIRM)
1) PackageOrder 락/상태검증(HOLD)
    2) Booking CONFIRM
       - 실패 → PackageOrder=FAILED
    3) Ticket CONFIRM
       - 실패 → Booking CANCEL(보상, 환불 stub) + Ticket CANCEL(가능하면) → PackageOrder=FAILED
    4) 성공 → PackageOrder=CONFIRMED



## Failure handling rules
- 보상 트랜잭션도 멱등해야 함(CANCEL 중복 호출 안전)
    - 오케스트레이터는 단계별 결과를 저장하고 재시도 시 이어서 진행
    - 최악의 경우 “미정 상태”는 운영자 개입(runbook)으로 처리할 수 있게 상태/로그를 남김



## Testing
- Integration(각 서비스 Testcontainers 또는 mock):
      - 티켓 hold 실패 시 숙소 hold가 복구되는지
      - confirm 2단계 중 2번째 실패 시 1번째가 cancel 되는지
      - idem 재시도(네트워크 타임아웃)에도 중복 확정 없음



## Acceptance Criteria
- 패키지 구매 시 “부분 확정”이 남지 않는다(성공/실패 모두)
    - 상태 머신이 문서화되어 운영자가 추적 가능
