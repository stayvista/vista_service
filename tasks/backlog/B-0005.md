# B-0005 — 에러 표준(Response Envelope + Error Contract) 확정


## Context
대규모 트래픽/다중 클라이언트(Web/User/Admin)에서 “에러를 표준화”하지 않으면:
- 프론트/모바일은 케이스마다 분기 지옥
- 운영자는 알람만 받고 원인을 못 찾음
- 재시도/대기열/멱등 같은 운영형 기능과 연결이 어려움

이 티켓은 **API 응답 엔벨로프 + 에러 계약**을 v1로 고정한다.


## Goal
- 모든 API 응답은 `request_id`를 포함한다.
- 에러 응답은 `error.code`를 기준으로 처리 가능해야 한다.
- Validation / NotFound / Conflict / RateLimit / Queue / Internal 대표 케이스가 동일 포맷으로 내려간다.



## Scope
- Success envelope & Error envelope 정의
- HTTP Status ↔ Domain Error Code 매핑 룰 확정
- `@RestControllerAdvice` 기반 전역 예외 처리기 구현(services 공통)
- 로그(구조화) + metrics 기본 추가
- 문서(ARCHITECTURE/RUNBOOK)에 표준 명시



## Non-goals
- 도메인별 세부 코드 전체 나열(Booking/Ticket 등)은 각 도메인 티켓에서 확장한다.
- 국제화(i18n) 메시지 카탈로그는 v2



## Response Envelope
### Success
```json
{
  "request_id": "01J0EXAMPLEQ0C2Z1Q8V4ZC9K7V",
  "data": {
    "booking_id": "bkg_01J0...",
    "status": "HOLD"
  }
}
```

### Error
```json
{
  "request_id": "01J0EXAMPLEQ0C2Z1Q8V4ZC9K7V",
  "error": {
    "code": "BOOKING_OVERBOOKED",
    "message": "Not enough inventory for requested dates",
    "details": {
      "room_type_id": 123,
      "dates": [
        "2026-02-10",
        "2026-02-11"
      ]
    }
  }
}
```

### 규칙
- `request_id`: 서버가 ULID/UUID로 생성(클라이언트가 `X-Request-Id` 제공 시 그대로 사용 가능)
- `data`: 성공 시 payload (null 금지)
- `error.details`: 디버깅/UX에 필요한 “안전한” 정보만 포함(PII/결제정보 금지)



## HTTP Status ↔ Error Code 매핑
| HTTP | 대표 error.code | 의미/예시 |
|---:|---|---|
| 400 | `VALIDATION_ERROR` | @Valid 실패, 타입 파싱 실패 |
| 401 | `UNAUTHORIZED` | 인증 실패 |
| 403 | `FORBIDDEN` | 권한 부족 |
| 404 | `NOT_FOUND` | 리소스 없음 |
| 409 | `CONFLICT` / `IDEMPOTENCY_REPLAY_MISMATCH` / `BOOKING_STATE_CONFLICT` | 상태 전이 충돌, 멱등키 충돌 |
| 429 | `RATE_LIMITED` / `QUEUE_REQUIRED` | 레이트 리밋 또는 대기열 |
| 500 | `INTERNAL` | 예기치 못한 오류 |

> **중요:** 동시성/과판매는 409(CONFLICT)로 통일(“누가 먼저 잡음”).



## Core Error Codes (v1 최소)
- `VALIDATION_ERROR` (400): 요청 파라미터/바디 검증 실패
- `NOT_FOUND` (404): 리소스 없음
- `CONFLICT` (409): 상태 충돌(버전/상태전이/멱등 mismatch 등)
- `RATE_LIMITED` (429): 레이트 리밋 초과
- `QUEUE_REQUIRED` (429): 대기열 토큰 필요/만료
- `INTERNAL` (500): 서버 내부 오류

추가(운영형):
- `IDEMPOTENCY_REPLAY_MISMATCH` (409): 같은 Idempotency-Key로 다른 요청 바디가 들어옴
- `BOOKING_OVERBOOKED` (409): 재고 부족/경쟁 패배
- `BOOKING_EXPIRED` (409): HOLD 만료
- `QUEUE_TOKEN_INVALID` (429): 대기열 토큰 만료/위조



## Implementation Notes (Kotlin/Spring)
- `ErrorResponse` DTO:
  - `requestId: String`
  - `error: ErrorBody(code: String, message: String, details: Map<String,Any?>)`
- `@RestControllerAdvice`에서 예외별 매핑:
  - `MethodArgumentNotValidException` → 400/VALIDATION_ERROR + field errors
  - `ConstraintViolationException` → 400/VALIDATION_ERROR
  - `EntityNotFoundException` → 404/NOT_FOUND
  - `DuplicateKeyException` → 409/CONFLICT (도메인별로 더 구체 코드로 래핑 가능)
  - `DataIntegrityViolationException` → 409/CONFLICT
  - `HttpRequestMethodNotSupportedException` → 405/METHOD_NOT_ALLOWED (선택)
- `request_id` 생성/전파:
  - Filter에서 `X-Request-Id`를 MDC에 넣고 응답에도 포함



## Observability
- Logs(구조화): `request_id`, `trace_id`, `user_id`, `path`, `status`, `error.code`
- Metrics:
  - `http_server_requests_seconds` (기본)
  - `api_errors_total{code=...}` (커스텀)
- Tracing:
  - span attribute에 `error.code` 기록



## Testing

- Integration(MockMvc):
