# B-0104 — Booking CONFIRM API (결제 스텁 + hold→sold 전환)



## Context
HOLD는 임시 점유이며, 결제가 성공하면 확정(BOOKED)으로 전환해야 한다.
    CONFIRM의 핵심은:
    - 만료/상태 충돌을 막고
    - 재고를 `hold → sold`로 **원자적으로 전환**하며
    - 외부 결제는 outbox로 분리(또는 v1은 스텁)하는 것이다.



## Goal
- `booking(status=HOLD)`를 `BOOKED`로 전환한다.
    - 모든 nights에 대해 `inventory_night.hold -= rooms`, `sold += rooms`를 원자적으로 수행한다.
    - 멱등(재시도) 보장.



## Scope
- `POST /v1/bookings/{bookingId}/confirm`
    - 사전 조건:
      - booking 존재
      - status=HOLD
      - expires_at > now
    - 결제:
      - v1: payment stub(항상 성공/실패 토글)
      - outbox 이벤트: `BookingConfirmed`, `PaymentAuthorized`(선택)



## Non-goals
- 실제 PG 연동/3DS/부분취소는 v2



## API Contract
### POST /v1/bookings/{bookingId}/confirm
- `X-Request-Id` (optional): 클라이언트가 생성한 요청 ID (없으면 서버 생성)
- `Idempotency-Key` (쓰기 API 필수): UUID 권장. 동일 요청 재시도 시 동일 결과 반환
- `Authorization` (optional in MVP): `Bearer <token>` (MVP에서는 `X-User-Id`로 대체 가능)
- `X-User-Id` (MVP only): 숫자 사용자 ID (인증 도입 전까지 임시)
Request:
```json
{
  "payment_method": "CARD",
  "payment_token": "paytok_test_123",
  "agree_terms": true
}
```
200 Response:
```json
{
  "request_id": "01J0...",
  "data": {
    "booking_id": "bkg_01J0...",
    "status": "BOOKED",
    "confirmed_at": "2026-02-07T14:01:20Z"
  }
}
```

Error:
- 404 `NOT_FOUND` (booking 없음)
- 409 `BOOKING_EXPIRED` (HOLD 만료)
- 409 `BOOKING_STATE_CONFLICT` (이미 BOOKED/CANCELLED)
- 409 `INVENTORY_INVARIANT_VIOLATION` (hold 부족 등, 데이터 이상)
- 409 `IDEMPOTENCY_REPLAY_MISMATCH`



## SQL (inventory transition)
```sql
-- booking_night에서 nights를 조회(오름차순)
    SELECT stay_date, rooms
    FROM booking_night
    WHERE booking_id = :bookingId
    ORDER BY stay_date;

    -- 각 날짜에 대해 hold->sold 전환 (영향 row=1이어야 함)
    UPDATE inventory_night
    SET hold = hold - :rooms,
        sold = sold + :rooms
    WHERE room_type_id = :roomTypeId
      AND stay_date = :stayDate
      AND hold >= :rooms;
```



## Transaction & Steps
1) booking row 조회 + (선택) `SELECT ... FOR UPDATE`로 booking 락
       - status/expires_at 검증
    2) payment stub 호출(또는 outbox로 비동기화)
       - v1 권장: “결제 승인” 자체는 빠르게 끝나야 하므로 stub은 in-process 10ms 이내
    3) booking_night를 날짜 오름차순 조회
    4) nights 각각 inventory_night UPDATE(hold>=rooms 조건)
       - 하나라도 실패하면 ROLLBACK + 409(INVENTORY_INVARIANT_VIOLATION)
    5) booking.status=BOOKED, confirmed_at set
    6) outbox_event insert(BookingConfirmed)
    7) COMMIT



## Idempotency
- CONFIRM은 반드시 Idempotency-Key를 요구한다.
    - 같은 키 재시도는 동일 booking 상태를 반환해야 한다.



## Observability
- Metrics:
      - `booking_confirm_requests_total{result=SUCCESS|EXPIRED|STATE_CONFLICT|ERROR}`
      - `booking_confirm_latency_seconds`
    - Logs: booking_id, user_id, result, payment_stub_result



## Testing
- Integration:
      - HOLD 생성 후 confirm → BOOKED 전환, inventory hold 감소/sold 증가
      - 만료된 hold confirm → 409 BOOKING_EXPIRED
      - 이미 confirm된 booking 재호출(동일 idem) → 동일 응답
    - Concurrency:
      - 같은 bookingId에 confirm 동시 10개 → 1개만 성공, 나머지는 state conflict 또는 idem 재사용



## Acceptance Criteria
- 재고 불변식 유지(hold 음수 불가)
    - outbox 이벤트가 생성되어 후속(알림/바우처/검색) 확장 가능
