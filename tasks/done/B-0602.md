# B-0602 — Deadlock/Lock wait 재시도 정책 공통화



## Context
재고 업데이트는 락을 잡는 작업이며, 경쟁이 심하면:
    - deadlock(1213)
    - lock wait timeout(1205)
    가 발생할 수 있다.

    재시도를 “아무데나” 넣으면 중복/부작용이 생기므로,
    **멱등+트랜잭션 경계**를 고려한 공통 재시도 정책이 필요하다.



## Goal
- 재시도 가능한 DB 예외를 식별하고, 짧은 백오프로 재시도한다.
    - 멱등키와 결합해 중복 예약을 만들지 않는다.



## Scope
- 대상 예외(MySQL):
      - Deadlock: SQLState=40001 / errno=1213
      - Lock wait timeout: errno=1205
    - 정책:
      - 최대 3회
      - backoff: 50ms, 150ms, 350ms (+ jitter)
      - 재시도는 “짧은 트랜잭션”에만 적용(booking hold/confirm/cancel)
    - 로그/메트릭:
      - `db_retry_total{reason=deadlock|lock_wait}`



## Non-goals
- 장시간 트랜잭션/배치 재시도는 별도 정책



## Implementation notes
- Spring:
      - `@Transactional` 밖에서 `RetryTemplate` 또는 `@Retryable`(주의) 사용
      - “재시도마다 새로운 트랜잭션”을 열도록 구성
    - Idempotency:
      - 재시도는 같은 Idempotency-Key 하에서만 안전



## Testing
- Integration:
      - 인위적으로 deadlock 상황을 만들어 retry가 작동하는지 확인
      - retry 후에도 최종 불변식이 깨지지 않는지 확인



## Acceptance Criteria
- 오픈런 부하 테스트(B-0601)에서 deadlock이 0이 아니어도 5xx로 전파되지 않고 성공/409로 수렴
