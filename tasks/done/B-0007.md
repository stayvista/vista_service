# B-0007 — Idempotency middleware 구현



## Context
모바일/웹은 네트워크 재시도, 더블클릭, 타임아웃으로 동일 요청이 여러 번 들어온다.  
    예약/결제 API에서 중복 처리는 곧 **중복 예약/중복 결제**로 이어진다.

    따라서 쓰기 API는 `Idempotency-Key`를 기본으로 강제한다.



## Goal
- 같은 `Idempotency-Key` + 동일 요청이면 **동일 응답**을 반환한다.
    - 같은 키로 다른 요청 바디가 들어오면 409로 차단한다.
    - 동시 요청(같은 키)이 겹쳐도 1회만 실제 실행되고 나머지는 대기/재사용한다.



## Scope
- `Idempotency-Key` 헤더 처리(Filter/Interceptor)
    - 저장소: MySQL 테이블 `idempotency_key`
      - key, user_id, endpoint, request_hash, response_status, response_body, created_at, expires_at
    - TTL 정책:
      - booking hold/confirm/cancel: 24h (권장)
      - ticket confirm/voucher: 7d (권장)
    - 에러 코드:
      - 409 `IDEMPOTENCY_REPLAY_MISMATCH`



## Non-goals
- GET 요청 캐싱/조건부 요청은 scope 아님
    - 글로벌 분산 키(멀티리전)는 v2



## Design
### 키 스코프
- `scope = user_id + endpoint + idempotency_key`
- endpoint는 **라우팅 단위**(예: `POST /v1/bookings/holds`)로 고정

### request_hash
- body(JSON)를 canonicalize(키 정렬) 후 SHA-256
- query string도 포함(있으면)

### 동작
1) 요청 진입: Idempotency-Key 없음 → 400(또는 endpoint별 강제) 
2) 테이블 조회
   - 존재하고 request_hash 동일 → 저장된 response 반환
   - 존재하고 request_hash 다름 → 409 IDEMPOTENCY_REPLAY_MISMATCH
3) 존재하지 않으면 INSERT(상태=IN_PROGRESS)
   - UNIQUE 충돌이면 누군가 먼저 넣음 → 다시 조회로 리턴/대기
4) 실제 핸들러 실행
5) 응답을 테이블에 저장(status/body), 상태=COMPLETED

### 동시성 (IN_PROGRESS)
- 같은 키가 동시에 들어오면 2번째 요청은:
  - (권장) 짧게 폴링(예: 50ms * 20) 후 완료되면 응답 재사용
  - 타임아웃이면 409/CONFLICT 또는 202/RETRY-LATER(선택)



## DB constraints
```sql
-- (예시) uk_idem_scope(user_id, endpoint, idem_key)
    -- request_hash mismatch 방지 및 응답 재사용
    CREATE TABLE idempotency_key (
      id BIGINT PRIMARY KEY AUTO_INCREMENT,
      user_id BIGINT NOT NULL,
      endpoint VARCHAR(120) NOT NULL,
      idem_key VARCHAR(80) NOT NULL,
      request_hash CHAR(64) NOT NULL,
      status VARCHAR(20) NOT NULL, -- IN_PROGRESS, COMPLETED
      response_status INT NULL,
      response_body_json JSON NULL,
      created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
      expires_at DATETIME(3) NOT NULL,
      UNIQUE KEY uk_idem_scope (user_id, endpoint, idem_key)
    );
```



## API usage example
### Example: booking hold 재시도
```bash
curl -X POST http://localhost:8083/v1/bookings/holds \
          -H 'Idempotency-Key: 9b7f6e2d-1c4b-4f0d-9e31-9d2d7d5c1f1a' \
          -H 'X-User-Id: 1001' \
          -H 'Content-Type: application/json' \
          -d '{"room_type_id":2001,"check_in":"2026-02-10","check_out":"2026-02-12","rooms":1}'
```
- 같은 Key로 같은 body를 반복 호출하면 booking_id가 동일해야 한다.



## Testing
- Unit:
      - request_hash canonicalization
      - mismatch 시 409 반환
    - Integration(MySQL):
      - 동일 key 재호출 → 동일 response
      - 동일 key 동시 10개 호출 → 실제 handler 1회만 실행(카운터로 검증)

- booking/ticket confirm 등 쓰기 API에서 Idempotency-Key가 필수로 강제됨
    - mismatch 케이스가 문서/테스트로 고정
