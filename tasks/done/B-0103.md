# B-0103 — Booking HOLD API (룸타입 재고형, 조건부 UPDATE)


## Context
숙소는 OTA에서 보통 **룸타입 재고형**으로 판매한다(“스탠다드 더블 20개”).  
예약 플로우는 결제/인증/3DS 등의 외부 의존이 있어 **즉시 확정(BOOKED)** 하면 과도한 롤백/환불이 발생한다.

따라서 v1은:
- 먼저 **HOLD(임시 점유, TTL 예: 10분)** 로 재고를 잠깐 확보
- 결제가 성공하면 CONFIRM에서 **HOLD → SOLD** 로 전환
- 시간이 지나면 만료 회수(Job)로 HOLD를 자동 해제

핵심은 동시성: 오픈런/특가에서 **과판매 0**을 DB가 보장해야 한다.


## Goal
- 사용자가 특정 `room_type_id`와 날짜 범위에 대해 HOLD를 생성할 수 있다.
    - 동시 요청에서도 `sold + hold <= total` 불변식이 깨지지 않는다(과판매 0).
    - 동일 요청 재시도는 Idempotency-Key로 **동일 결과**를 반환한다.



## Scope
- `POST /v1/bookings/holds`
    - 재고 차감: `inventory_night(room_type_id, stay_date)`에 대해 날짜별 **조건부 UPDATE**
    - `booking` + `booking_night` 레코드 생성 (status=HOLD, expires_at 설정)
    - 실패 시 전체 ROLLBACK (부분 성공 금지)



## Non-goals
- 결제/확정(CONFIRM)은 B-0104
    - 쿠폰/포인트/가격 규칙 엔진은 v2 (v1은 price_snapshot 단순 저장)



## API Contract
### Endpoint
- **POST** `/v1/bookings/holds`

### Headers
- `X-Request-Id` (optional): 클라이언트가 생성한 요청 ID (없으면 서버 생성)
- `Idempotency-Key` (쓰기 API 필수): UUID 권장. 동일 요청 재시도 시 동일 결과 반환
- `Authorization` (optional in MVP): `Bearer <token>` (MVP에서는 `X-User-Id`로 대체 가능)
- `X-User-Id` (MVP only): 숫자 사용자 ID (인증 도입 전까지 임시)

### Request Body
```json
{
  "room_type_id": 2001,
  "check_in": "2026-02-10",
  "check_out": "2026-02-12",
  "rooms": 1,
  "guests": {
    "adults": 2,
    "children": 0
  },
  "price": {
    "currency": "KRW",
    "amount_total": 240000
  },
  "user_note": "늦은 체크인 예정"
}
```

### 201 Response
```json
{
  "request_id": "01J0...",
  "data": {
    "booking_id": "bkg_01J0F0ABCDEF1234567890",
    "status": "HOLD",
    "expires_at": "2026-02-07T14:05:00Z",
    "hold": {
      "room_type_id": 2001,
      "nights": [
        {
          "stay_date": "2026-02-10",
          "rooms": 1
        },
        {
          "stay_date": "2026-02-11",
          "rooms": 1
        }
      ]
    },
    "price_snapshot": {
      "currency": "KRW",
      "amount_total": 240000
    }
  }
}
```

### Error Responses
- 400 `VALIDATION_ERROR`
  - check_in/check_out 형식 오류, check_out <= check_in, rooms <= 0 등
- 404 `NOT_FOUND`
  - room_type_id 없음/비활성
- 409 `BOOKING_OVERBOOKED`
  - 기간 중 하루라도 재고 부족(경쟁에서 패배)
- 409 `IDEMPOTENCY_REPLAY_MISMATCH`
  - 같은 Idempotency-Key로 다른 바디
- 429 `RATE_LIMITED` / `QUEUE_REQUIRED`



## Data Model / SQL
### 관련 테이블 (v1 스키마 기준)
- `inventory_night(room_type_id, stay_date, total, hold, sold, updated_at)`
  - **PK** `(room_type_id, stay_date)`
- `booking(id, user_id, room_type_id, status, rooms, check_in, check_out, expires_at, price_snapshot_json, idempotency_key, created_at, ...)`
- `booking_night(booking_id, stay_date, rooms)` (조회/정합성/회수 용)

### 조건부 UPDATE (과판매 방지 핵심)
각 날짜에 대해 아래 UPDATE를 수행한다. 영향 row=1이면 성공, 0이면 실패:
```sql
UPDATE inventory_night
SET hold = hold + :rooms
WHERE room_type_id = :roomTypeId
  AND stay_date = :stayDate
  AND (hold + sold + :rooms) <= total;
```

> `inventory_night`가 없는 날짜(행이 없음)인 경우:
- Admin이 미리 total을 넣도록 강제(B-0102), 또는
- v1에서는 없으면 404/NOT_FOUND 처리(권장: 운영 실수 조기 노출)

### Booking 레코드 생성
- 모든 날짜 UPDATE가 성공한 뒤 `booking(status=HOLD, expires_at=now+10m)` 생성
- `booking_night`에 연박 날짜를 모두 insert



## Transaction & Concurrency
### 트랜잭션 단계(권장 순서)
1. `room_type` 존재/상태 확인(READ)
2. 날짜 리스트 생성: `[check_in, check_out)` (check_out 제외)
3. **(중요) 날짜 오름차순**으로 `inventory_night` 조건부 UPDATE 반복
   - 하나라도 affected_rows=0 → 즉시 예외 → ROLLBACK
4. `booking` insert (status=HOLD, expires_at)
5. `booking_night` batch insert
6. COMMIT

### 왜 날짜 오름차순인가?
- 여러 트랜잭션이 같은 날짜 범위를 업데이트할 때 **락 순서**를 고정해 데드락 확률을 낮춘다.

### 격리수준
- MySQL InnoDB 기본(REPEATABLE READ)에서도 위 패턴은 안전하다.
- 핵심은 “조건부 UPDATE 자체가 원자적”이라는 점.

### Idempotency
- 키 스코프: `(user_id, idem_key, endpoint)` 권장
- 동일 키 재호출 시:
  - request_hash 동일 → 저장된 response 반환(201)
  - request_hash 다름 → 409 `IDEMPOTENCY_REPLAY_MISMATCH`



## Timeout / Latency Budget
- P99 목표(서버): **< 150ms** (캐시 미사용, DB 왕복 2~N회)
    - 연박 N일이면 UPDATE N번이므로 N이 길어질수록 증가
      - v1 정책: 최대 숙박 30박 제한(Validation)
    - 락 대기 방지:
      - `innodb_lock_wait_timeout` 기본 50s는 너무 김 → 앱 레벨에서 timeout(예: 2s) + 재시도 정책(B-0602)



## Observability
- Logs(booking_hold):
      - `request_id`, `user_id`, `room_type_id`, `nights`, `rooms`, `result=SUCCESS|OVERBOOKED|ERROR`, `latency_ms`
    - Metrics:
      - `booking_hold_requests_total{result=...}`
      - `booking_hold_latency_seconds` (histogram)
      - `inventory_update_failed_total` (overbook)
    - Tracing:
      - span: `booking.hold`
      - attributes: `room_type_id`, `night_count`, `rooms`, `overbooked=true/false`



## Testing
### Unit
    - 날짜 리스트 생성 로직(check_out 제외)
    - Validation: check_out > check_in, rooms>0, max_nights<=30

    ### Integration (Testcontainers: MySQL)
    - Case: 충분한 재고 → HOLD 성공(booking/status/expires_at 검증)
    - Case: 재고 부족(중간 하루 total=0) → 409 BOOKING_OVERBOOKED, DB 변화 없음(롤백)
    - Case: Idempotency:
      - 동일 Idem-Key & 동일 바디 → 같은 booking_id 반환
      - 동일 Idem-Key & 다른 바디 → 409 IDEMPOTENCY_REPLAY_MISMATCH

    ### Concurrency (핫키)
    - 준비: 특정 room_type, 특정 날짜에 total=1
    - 동시에 20개 스레드가 HOLD(rooms=1) 호출
    - 기대: 성공 1, 실패 19 (409), 최종 `hold=1`, `sold=0`
    - 추가: total=10이면 성공 10, 실패 10



## Rollout / Ops
- Feature flag: `booking.hold.enabled` (환경별 on/off)
    - 장애 시 대응:
      - overbook 급증: 대기열(B-0502) 임계치 낮추기 / rate limit 강화(B-0501)
      - DB lock wait 증가: max_nights 제한 강화, 재시도 백오프 조정(B-0602)
