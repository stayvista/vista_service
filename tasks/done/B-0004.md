# B-0004 — 공통 Observability(로그/메트릭/트레이스) 골격



## Goal
수백만 사용자 트래픽을 전제로, 장애/지연/과판매 이슈를 **재현 없이** 파악할 수 있게
    모든 서비스에 공통 Observability를 강제한다.



## Scope
- request_id/trace_id 전파:
      - inbound: `X-Request-Id` 수용/생성
      - outbound: 내부 서비스 호출 시 헤더로 전파
    - Structured logging:
      - 필수 필드: `timestamp`, `level`, `service`, `request_id`, `trace_id`, `path`, `method`, `status`, `latency_ms`
      - 도메인 필드(예약): `booking_id`, `room_type_id`, `result`
    - Metrics(Micrometer):
      - http server 기본 metrics + 커스텀 카운터/히스토그램
    - Tracing(OpenTelemetry):
      - 주요 스팬 이름 규칙, error.code attribute



## Non-goals
- Grafana/Datadog 대시보드 JSON 배포는 v2 (RUNBOOK에 지표 목록만 우선)



## SLO/Latency Budget (초기)
- Search API P95 < 200ms, P99 < 500ms
    - Booking HOLD P95 < 150ms, P99 < 300ms
    - Booking CONFIRM P95 < 250ms, P99 < 600ms
    - 오류율(5xx) < 0.1%



## Instrumentation requirements
- 모든 Controller에:
      - request_id 포함한 응답
      - 에러 시 `error.code`
    - DB:
      - slow query 로그(로컬), 운영은 APM으로 대체
    - Kafka:
      - outbox relay lag, publish 실패 카운터



## Acceptance Criteria
- 임의 API 호출 시:
      - 로그에서 request_id로 end-to-end 추적 가능
      - actuator/metrics에서 latency histogram 확인 가능
    - RUNBOOK에 “어디를 보면 원인을 찾는지” 절차가 존재
